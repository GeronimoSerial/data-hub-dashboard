#### Shared forecast cache contract (requested by the user)

**Proposed design:** compute the immutable forecast once per published run
(normally every six hours), persist the compact derived result in shared
application storage, and serve it to all authorized users. Reuse PostgreSQL
rather than introducing another service solely for this cache; finalize the
additive storage shape during implementation review.

- Key immutable results by environment, run ID, calculation/rules version,
  cutoff and relevant geographic/reference versions. Prefer one canonical
  result per run with cheap horizon/department/ranking selection over a full
  recomputation for each user's filter combination.
- Publish the complete result atomically and invalidate immediately on a newer
  run/version. Six hours is the expected refresh cadence, not permission to
  hide a newer run or label expired data as current. Preserve the original
  publication/validity times and explicit stale/no-data state on job failure.
- Use a shared lease/uniqueness constraint and bounded waiting to prevent
  simultaneous cold-cache requests from triggering duplicate calculations.
  A local promise may deduplicate within one process, but is not the shared
  cross-process guarantee. Do not cache failures as successful forecasts.
- Authorize before reading cached data and apply any audience/scope filtering
  before returning it. Do not use a public CDN cache for authenticated payloads.
- Keep live confirmed affectations and their exclusion from access KPIs fresh:
  the current endpoint calls `listarEscuelasMapa`. Compose that live overlay
  separately or invalidate it on report changes, never freeze it for six hours.
- Radar Meteorological summaries use their own run identity and dependencies
  (SMN alerts and verification can change sooner). Do not give every source
  the six-hour forecast TTL or reuse the existing process-local summary `Map`
  as proof that all users already share the computation.
- Verify concurrent cold requests across two processes cause one calculation;
  warm requests reuse it, publication invalidates it, failures release the
  lease, old runs remain isolated, and report changes refresh live KPIs.

Bound SQL reads first: caching an unbounded cold calculation still permits the
first request after restart or invalidation to exhaust memory.
