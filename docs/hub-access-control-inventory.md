## Current roles, permissions, and known destinations

- Application roles (`lib/acl.ts`, `lib/auth.ts`): `admin`, `editor`, `consulta`, `director_nivel`, `operador_establecimiento`; Better Auth's default role is `consulta`, public sign-up is disabled, email/password is enabled (minimum 8), and `adminRoles` is only `admin`.
- Resource ACL: banned users are denied; drafts require staff (`admin`/`editor`); admin/editor can open resources; other roles are constrained by selected-resource access (when configured), resource audience, and jurisdiction. Existing page/API policies additionally apply CUE, nominal-data and write permission checks.
- GE role-to-destination mapping is recorded above. The code establishes SSO behavior, not a representative sample of deployed users. T1 did not inspect a production DB or credentials. No authoritative representative account records/destination inventory was available in this checkout; preserve existing accounts/special destinations by a read-only, authorized snapshot before rollout migration/activation rather than guessing defaults.
- `/api/usuarios` creates accounts with administrator-assigned passwords; the user administration model currently stores role, blocked state, jurisdiction IDs and resource access (`todos`/`seleccionados` plus IDs). User list/mutation functions and last-admin checks live in `lib/usuarios.ts`.

### T4a server catalog/read visibility (2026-10-23)

`filterCatalogForSections` in `lib/db/hub-catalog-for.ts` is the shared boundary: it applies `resourceInSections` from the centralized hub policy to the full catalog, then retains only taxonomy rows referenced by visible resources. Because `buildCatalogResponse` is shared, `/api/hub` and staff `/api/hub/admin` use the same filter; `loadCatalogFor` reuses it for SSR initial HTML and the client refetch hits the same endpoint contract.
